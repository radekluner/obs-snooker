# AGENTS.md

## About the project

`obs-snooker` is a plugin/script for OBS Studio intended for streaming snooker matches.

Goals of the project:
- Display a **scoreboard overlay** directly in the video (as a source/scene in OBS), showing the current match score.
- At the same time, display the current score in a **separate window** outside of OBS – this window will run on a different monitor (typically for the operator/referee who controls or watches the score).

There are two OBS-facing outputs for the score, both kept in sync from the same in-process `MatchState`, and users can enable either or both:
1. **Plain OBS text source** (`text_gdiplus` / `text_ft2_source`) – simple, no extra setup, but no custom graphics/transparency beyond what the text source itself supports.
2. **Browser-source overlay** – a small local HTTP server (`obs_snooker.overlay_server.OverlayServer`) serves a styled HTML/CSS/JS scoreboard page. Add it in OBS as a **Browser Source** pointed at `http://127.0.0.1:<port>/overlay` (default port `8710`, configurable in the script's properties panel). This is the recommended option for a polished, TV-broadcast-style look: a full-width "lower third" bar docked to the bottom of the screen, with dark navy name plates (each with a small gold country-code badge, e.g. "CZE", next to the player's name), a gold trim line along the top, deep-red score boxes with large gold digits showing the **in-progress frame score** (the dominant number - it changes shot-by-shot and needs to be readable from across the room), a small dark "frames won" pill centered between the two score boxes (the match score, which changes much less often so it stays secondary/small), a CSS-triangle turn-indicator arrow pointing from each name plate toward that player's score box (lit up green and pulsing for whoever is on the shot), an optional race-to/best-of label below the bar, and an optional match-title pill (e.g. "World Championship - Final") centered above it – all with a transparent page background so only the graphic shows over the camera feed. This composition (full-width bar, flag/country badge, big score boxes either side of a small frames-won pill, turn-indicator arrow) is *inspired* by the general layout of televised snooker coverage (e.g. the BBC's), but deliberately uses this project's own original color palette (dark navy, gold, deep red) rather than copying any specific broadcaster's actual colors, logos, or exact graphic templates/trade dress.

## Domain model: real snooker scoring semantics

`MatchState` (in `obs_snooker/match_state.py`) models a snooker match, not just a flat "score":

- **Frames won** (`player1_frames` / `player2_frames`) – the actual *match* score. A match is won by the first player to reach `frames_to_win` frame wins.
- **Frame score** (`player1_frame_score` / `player2_frame_score`) – points scored so far in the *current, unfinished* frame. Reset to 0-0 whenever a frame ends (`win_frame`) or is manually re-racked (`reset_frame_scores`).
- **`frames_to_win`** – the race format, e.g. `10` for a "best of 19 frames" final (`best_of` is derived as `2 * frames_to_win - 1`).
- **`current_player`** (`1` or `2`) – who currently has the "on the table" / turn indicator. Toggled explicitly via `switch_turn()`/`set_current_player()`, and automatically toggled by `win_frame()` (the break is assumed to alternate between frames, as a simplification of real referee-tracked play).
- **`winner()`** – returns the winning player number once `frames_to_win` is reached, or `None` while the match is in progress.
- **`reset_frame_scores()`** vs **`reset_match()`** – the former only clears in-progress frame points (e.g. a re-rack after a foul dispute); the latter resets frames won, frame scores, and the turn indicator for a brand new match, while leaving player names, `frames_to_win`, and `match_title` untouched (those are match *configuration*, not *progress*).

This same model drives all three outputs identically:
- The plain OBS text source shows a compact one-line summary via `as_overlay_text()` (e.g. `>Alice 4 (45) - (12) 3 Bob`, where `>`/`<` marks whose turn it is).
- The Tkinter scoreboard window (see below) shows the in-progress frame score as the dominant digits in a deep-red box, a smaller gold "frames won" count in a rounded pill below it, a rounded green/grey "ON THE TABLE" pill per player indicating whose turn it is (plus a thin colored border around the active player's whole panel as a secondary cue), and a race-to/best-of label - visually matching the browser overlay's color palette (dark navy panels, gold accents, deep red score boxes) for a consistent, modern look across both outputs.
- The browser overlay shows the same information as a full-width broadcast-style bar: the in-progress frame score as the main, large score boxes (`.score-box`), a single small "frames won" pill (`.frames-center`, showing both players' frame counts, e.g. "4 – 0") between them, a country-code badge (`.country-badge`) next to each name, and a turn-indicator arrow (`.turn-indicator`) per player. Both the frame-score boxes and the frames-won numbers briefly "pop" (scale up via the `.bump` CSS class, toggled by `overlay.js`) whenever their value changes.

Current state: early development. Code is split into:
- `obs_snooker/match_state.py` – pure scoring logic (`MatchState`), no OBS or GUI dependency.
- `obs_snooker/scoreboard_window.py` – the Tkinter scoreboard window (for the second monitor, sized `1920x1080`), depends only on `obs_snooker.match_state` (no `obspython`). Supports F11/Escape to toggle real OS fullscreen once dragged onto the second monitor. **Runs as a standalone OS process** launched via `python -m obs_snooker.scoreboard_window --url <score endpoint>` (see "Scoreboard window process" below for why).
- `obs_snooker/overlay_server.py` + `obs_snooker/overlay_assets/` (`overlay.html`/`.css`/`.js`, `control.html`/`.css`/`.js`) – the browser-source overlay's HTTP server and static assets (broadcast overlay + the interactive control panel, see "Browser-based control panel" below), also independent of `obspython`.
- `obs_snooker/darwin_keycode_patch.py` – macOS-only workaround for a real `pynput`/OBS crash (see "pynput's macOS keyboard backend crashes OBS..." below); independent of `obspython`, a no-op on non-macOS platforms.
- `obs_snooker/player_database.py` – local JSON-backed player roster (`Player`/`PlayerDatabase`), no OBS or GUI dependency.
- `obs_snooker/player_manager_window.py` – the Tkinter add/rename/delete UI for the player roster (see "Player database" below). **Runs as a standalone OS process**, same reasoning as the scoreboard window.
- `obs-snooker.py` – thin OBS entry point/glue script (loaded by OBS itself): wires up `obspython` callbacks, the `pynput` Bluetooth-keyboard listener, the overlay server, and launches/terminates the scoreboard window's and player manager's subprocesses.
- `tests/` – pytest suite covering `match_state`, `overlay_server`, and `player_database` (always run, no display needed), `scoreboard_window` and `player_manager_window` (auto-skipped when Tkinter/a display isn't available), and `darwin_keycode_patch` (auto-skipped on non-macOS).

Functionally, the script:
- reacts to key presses from a Bluetooth keyboard and updates the plain OBS text source,
- launches the standalone scoreboard window process showing frames won, current-frame score, and turn indicator for both players, meant to be moved to a second monitor,
- runs the browser-source overlay's HTTP server so OBS can render the styled scoreboard graphic as a lower-third-style overlay on the camera feed, and so the scoreboard window process has a live JSON endpoint to poll,
- lets players be picked from a reusable local database (see "Player database" below) instead of only typed free-text, with a separate standalone window for managing that roster,
- exposes player selection/names, the race format (`frames_to_win`), a configurable `points_per_shot` for the "+points" buttons, per-player "wins frame"/"+points" buttons, "switch turn", "reset frame", "reset match" buttons, a "show scoreboard window" button (relaunches the process if it was closed, e.g. by accident, without needing to reload the script), an optional manual Python interpreter override, and the overlay port through the OBS script properties panel, keeping the text source, the scoreboard window process, and the browser overlay in sync.

## Scoreboard window process: why it is a separate OS process, not in-process Tk

Earlier versions of this project created the `ScoreboardWindow`'s Tk root directly inside OBS's own embedded Python interpreter, pumping its event loop via `obs.timer_add` on OBS's main thread. **This turned out to cause a real, reproducible OBS crash on macOS**: OBS itself is a Qt/Cocoa application with its own `NSApplication` instance, and Tk's Cocoa backend does not reliably coexist with a foreign host's `NSApplication` when creating widgets - the observed crash was a `SIGABRT` inside Tk/Tcl's Cocoa color-handling code (`Tk_Alloc3DBorderFromObj` → `TkpGetColor` → an Objective-C `doesNotRecognizeSelector` exception → `abort()`), triggered simply by creating a `tk.Frame` with a background color. This is not something fixable from Python application code - it is a fundamental incompatibility between embedding Tk's own Cocoa integration inside another native Cocoa/Qt host process.

The fix: `obs-snooker.py` now launches the scoreboard window as a **separate OS process** (`subprocess.Popen([python_executable, "-m", "obs_snooker.scoreboard_window", "--url", <score endpoint>])`), which gets its own dedicated main thread and its own, independent `NSApplication` - completely avoiding the conflict. That process runs a normal `Tk.mainloop()` (safe here, since it owns the whole process) and keeps itself updated by polling the overlay server's `/api/score` JSON endpoint every 400ms via `urllib`, exactly like `overlay.js` does in the browser overlay - see `obs_snooker/scoreboard_window.py`'s `_run_live()`/`_state_from_payload()`.

Practical implications:
- The overlay server (`OverlayServer`) must be running before/while the scoreboard window process is useful, since that's now its only source of live data. `obs-snooker.py`'s `script_load()` starts the overlay server before launching the scoreboard window process for this reason.
- `obs-snooker.py` needs a real, launchable Python interpreter path to spawn the subprocess. OBS's embedded interpreter does not reliably set `sys.executable` to a real python binary (it may point at OBS itself), so `_find_python_executable()` tries a few candidate paths (`sys.executable` if it looks like a python binary, `<exec_prefix>/bin/python3.x`, `<exec_prefix>/bin/python3`) and falls back to a script property, **"Python interpreter (for scoreboard window)"**, that the user can set manually if auto-detection fails for their setup.
- `ScoreboardWindow` (the class itself) is unchanged and still directly unit-testable/constructible in-process in `tests/test_scoreboard_window.py` - only the way `obs-snooker.py` *launches* it for real OBS usage changed. `pump()` still exists on the class for that direct/testing use case.

## Player database

Instead of only typing free-text names, users can maintain a reusable roster of players (name + optional country/nationality code, e.g. for a future flag icon) and pick "Player 1"/"Player 2" from a dropdown in OBS's properties panel:

- `obs_snooker/player_database.py` – pure data layer (`Player`, `PlayerDatabase`), no OBS or GUI dependency. Backed by a single local JSON file (default: `players.json` next to `obs-snooker.py`), not SQLite - deliberately, to avoid depending on any stdlib module (even `sqlite3`) beyond `json`/`pathlib`, given the real history of OBS-bundled Python distributions missing modules that would otherwise seem safe (see "Reduced/mismatched OBS Python environments" below). Every mutating method (`add_player`/`update_player`/`remove_player`) saves to disk immediately. Corrupt/missing files are treated as an empty database rather than raising.
- `obs_snooker/player_manager_window.py` – the actual add/rename/delete UI, a small Tkinter window. **Also launched as a separate OS process** (`python -m obs_snooker.player_manager_window --db <path>`), for the exact same reason as the scoreboard window (see "Scoreboard window process" above) - any Tk widget creation inside OBS's own process risks the same Cocoa crash. It owns the database file directly (reads once on start, writes on every change); there is no live polling needed since there's no "in-progress match" aspect to a player roster.
- `obs-snooker.py` integration: two `OBS_COMBO_TYPE_LIST` dropdowns (`player1_id`/`player2_id`) populated from `player_db.list_players()`, plus a "(custom name below)" sentinel option (value `""`) that falls back to the existing free-text `player1_name`/`player2_name` fields for one-off matches that don't need to be saved to the roster. A "Manage players..." button launches the manager subprocess; a "Refresh player list" button re-reads the JSON file and repopulates both dropdowns in place (`obs_property_list_clear` + `obs_property_list_add_string`), since OBS's properties panel has no way to notice the file changed in the separate manager process while the panel is already open.
- `MatchState` gained `player1_country`/`player2_country` (default `""`), threaded through `OverlayServer`'s `/api/score` JSON and `scoreboard_window._state_from_payload()`. Rendered in the browser overlay as a small text badge (`.country-badge`, e.g. "CZE") next to each player's name - not yet rendered in the Tkinter scoreboard window, and not yet an actual flag graphic (would need a country-code-to-flag-asset mapping, deferred until actually requested).
- **Sort order:** `PlayerDatabase.list_players()` sorts by **surname** (the last whitespace-separated token of `name`, e.g. "Ronnie O'Sullivan" sorts under "O"), not by first name, since that's how players are normally looked up in a long roster. Falls back to the full name as a secondary sort key for stability, and to the full (stripped) name itself if it has no spaces. This is a simple heuristic, not true name parsing (it won't handle e.g. "van der Berg"-style multi-word surnames specially), which is an accepted tradeoff for a single free-text `name` field rather than separate first/last name fields.
- **Long player names in the overlay and scoreboard window:** both UIs auto-shrink the player-name font as names get longer, since a fixed font size would either overflow the layout or force the whole scoreboard/name-plate wider for one long name. Both independently implement the same two length thresholds (14 and 20 characters) to decide between a normal/"long"/"very-long" size tier - kept in sync by convention rather than a shared constant, since one lives in Python (`scoreboard_window.py`'s `_name_font_size()`) and the other in CSS/JS (`overlay.css`'s `.player-name.long`/`.player-name.very-long` classes, applied by `overlay.js`'s `applyNameSizing()`). `overlay.css` additionally keeps a `max-width` + `text-overflow: ellipsis` safety net on `.player-name` in case a name is still too wide even at the smallest tier; the scoreboard window instead sets `wraplength` on the name label so an extreme case wraps to a second line rather than being clipped or stretching the panel. The scoreboard window's two player columns also use a `grid_columnconfigure(..., uniform="player_panel")` group so both panels are always exactly the same width regardless of name length, and the name label's `wraplength` is recomputed live from the panel's actual rendered width (via a `<Configure>` binding) rather than a fixed guess, so it can never overflow past the panel edge on any window/monitor size.

## OBS Hotkeys (preferred way to control a live match)

In addition to the buttons in this script's own Scripts-dialog properties panel, the common scoring actions are also registered as native **OBS Hotkeys** via `obs.obs_hotkey_register_frontend()` in `obs-snooker.py`'s `register_hotkeys()`:

- Generic `+points`/`-points` for either player (adds/subtracts the configured "points per shot" amount - `-points` is for undoing a mis-click).
- **Per-ball-value potting**: `player{1,2}_pot_{red,yellow,green,brown,blue,pink,black}`, each worth its real snooker point value (1 through 7) - built programmatically from the `_BALL_VALUES` list rather than the generic points-per-shot amount, so e.g. "potted black" always adds exactly 7 regardless of whatever the generic field is set to. This is the realistic way to operate a live scoreboard (one press per pot, matching the ball that actually went in), rather than relying only on a single generic "+1" button.
- `wins frame` for either player, `switch turn`, `reset frame score`.

These show up in OBS's own **Settings -> Hotkeys** panel (search for "Snooker"), completely separate from this script's Scripts dialog, and can be bound to any key/combo there - including keys on a Bluetooth keyboard - without needing to reopen this script's panel during a live match. Key bindings are persisted across OBS restarts via `script_save()`/`script_load()` (`obs_hotkey_save`/`obs_hotkey_load`, stored as an `obs_data_array_t` per hotkey under a `hotkey_<name>` key in the script's settings). `unregister_hotkeys()` is called from `script_unload()` for a clean teardown. Note: `reset_match` deliberately has **no** hotkey (only a Scripts-panel button), since it's a destructive, rarely-used action that shouldn't risk being triggered by an accidental key press mid-stream - manual score correction (below) is the safer way to fix an in-progress mistake instead of resetting everything.

### Manual score correction

Mistakes happen (mis-clicks, a ball potted off-screen before the scorer reacts, resuming a match that was tracked on paper, etc.), so `MatchState` exposes two direct-override methods, independent of the usual increment-based flow:

- `set_frame_score(player, value)` - directly sets a player's in-progress frame score (clamped at 0), as an alternative to nudging it back into place with repeated `add_frame_points()` calls.
- `set_frames(player, value)` - directly sets a player's frames-won tally (clamped at 0), *without* the side effects `win_frame()` has (it does **not** reset frame scores or alternate the turn indicator - a manual correction shouldn't also reset the in-progress frame or flip whose turn it is).

These are exposed in `obs-snooker.py`'s Scripts-panel properties under a **"Manual score correction"** group: an int field + "Set" button per player per value (4 fields, 4 buttons total: `player{1,2}_frame_score_correction`/`player{1,2}_frames_correction`). Deliberately **not** exposed as hotkeys, since OBS hotkeys are simple press/release booleans with no way to carry an arbitrary numeric value - a one-off settings-panel edit is the right interaction for an infrequent corrective action like this.

Historical note: the `pynput`-based Bluetooth-keyboard listener (`start_keyboard_listener()`/`on_press()`) predates the OBS-hotkey integration and is still present, but its `on_press()` handler is only a placeholder/demo (it just prints test strings to the plain text source) - it is **not** wired to any real match-scoring action. OBS's own hotkey system is the recommended way to drive the scoreboard from a keyboard now; the `pynput` listener is kept mainly as a reference for the real-crash workaround documented below, and could be repurposed or removed in the future if it's no longer needed.

## Freeze reference overlay (referee tool)

A referee tool to help restore a disturbed snooker table to its previous state: takes a screenshot of a configured camera source and shows it as a semi-transparent "ghost" image on top of the live feed in the current scene, so the referee can see exactly where the balls were and nudge them back into place. Exposed as three separate actions (both as Scripts-panel buttons in the "Freeze reference overlay (referee tool)" group, and as OBS Hotkeys), since a single toggle alone can't cover "retake while already showing":

- **Freeze now** (`show_freeze_overlay()`) - always takes a brand new screenshot and shows it, even if a freeze is already displayed. This is the one to use if the first freeze was taken at a bad moment (camera lag, wrong instant) and needs retaking without first hiding it.
- **Hide freeze overlay** (`hide_freeze_overlay()`) - just hides the overlay (keeps the underlying source around for a fast next freeze).
- **Toggle freeze reference overlay** (`toggle_freeze_overlay()`) - convenience action for a single button/hotkey workflow: hides if currently shown, otherwise takes a new freeze and shows it. Note this means retaking while already shown needs two presses of *this* action (hide, then show) - use "Freeze now" directly instead if you want to retake in one press regardless of current visibility.

There is no `obspython` API to capture a source's rendered frame directly into memory/another source - the only officially exposed capture mechanism is `obs_frontend_take_source_screenshot()`, which always writes a file to disk. So this feature necessarily goes through a screenshot file, but only as a one-time transient hand-off: the file's contents get loaded into a **persistent, reusable hidden scene item** (an `image_source` named `"Snooker Freeze Reference"`), which is what the user actually interacts with afterwards (toggle visibility, adjust opacity) - not the file itself.

Implementation (`obs-snooker.py`'s `show_freeze_overlay()`/`hide_freeze_overlay()`/`toggle_freeze_overlay()`):
1. `obs.obs_frontend_take_source_screenshot(camera_source)` triggers OBS's own screenshot mechanism for the configured "Camera source:" (any source, picked from a dropdown of all sources - `_populate_source_list()`/`freeze_camera_source` setting).
2. Since that API writes an image file asynchronously without returning a path, `_screenshot_output_dir()` guesses the destination folder (assumes it matches OBS's configured *recording* output path, via `obs_frontend_get_current_record_output_path()` - confirmed correct in practice, though not a documented guarantee), and `_wait_for_new_screenshot_async()` polls that folder for a new image file (`.png`/`.jpg`/`.jpeg`/`.bmp`) that wasn't there before the screenshot was triggered.
   - **Important**: this polling is driven by `obs.timer_add()` (a periodic OBS-level callback), **not** a blocking `time.sleep()` loop. `obs_frontend_take_source_screenshot()` is itself asynchronous and needs OBS's own main/UI loop to keep running in order to actually finish writing the file - a naive blocking loop on the same thread that triggered the screenshot would prevent OBS from ever completing it, causing a timeout on every attempt regardless of whether the directory guess was correct (this was a real bug hit during development: the directory guess was right, but the blocking-`sleep()` version always timed out). `_freeze_poll_tick()` is the timer callback; it's removed via `obs.timer_remove()` once the file is found or the 8-second timeout (`_FREEZE_POLL_TIMEOUT_S`) elapses. `script_unload()` also calls `obs.timer_remove(_freeze_poll_tick)` as a safety net in case a poll is still in flight.
   - **Also important**: a file can appear in the directory listing *before* OBS has finished writing its actual pixel data to it (created but still 0-byte/truncated at that instant) - loading it as the `image_source`'s "file" setting at that moment fails to decode silently (the scene item's "file" path looks correctly set in OBS's own UI, but nothing is actually drawn - this was a second real bug hit during development, after the async-polling fix above). So once a candidate file is detected, `_freeze_poll_tick()` switches to a second phase that re-checks the file's size on each subsequent tick and only hands it to `on_found()` once its size has been unchanged (and non-zero) for `_FREEZE_POLL_STABLE_TICKS` (3) consecutive polls - i.e. it waits for the write to actually finish, not just for the file to exist.
3. Once found, the persistent `image_source` named `"Snooker Freeze Reference"` is created (first time) or reused/updated in place (every subsequent freeze) pointing at that screenshot file.
4. `_copy_sceneitem_transform()` copies the camera source's scene-item position/scale/rotation/bounds/alignment onto the freeze-overlay item, so the frozen image lines up exactly 1:1 with the live camera underneath it, regardless of how the camera has been cropped/positioned in the scene.
5. `_ensure_opacity_filter()` adds/updates a built-in **"Color Correction"** filter (internal id `color_filter`, property `opacity` as a 0-100 double) on the freeze-overlay source to make it semi-transparent, using the configured `freeze_opacity` setting (default 50%, adjustable any time from the Scripts panel - re-applied on every freeze).
6. The scene item is shown (`obs_sceneitem_set_visible(..., True)`). Toggling off just hides it (`False`) rather than deleting it, so the next freeze is a fast in-place update rather than recreating everything from scratch - this is also what makes opacity/visibility adjustments feel instant to the user, since there's no screenshot round-trip needed except when actually re-freezing a new moment.

**Known caveats / unverified assumptions** (this feature touches obspython scene/filter/screenshot APIs not used anywhere else in this project; the async-polling fix above was applied after a real timeout was reported, but full behavior has still not been exhaustively verified against every OBS version/platform - test carefully in your actual OBS before relying on it live):
- The assumption that screenshots land in the *recording* output folder has been confirmed correct in at least one real OBS setup (matched a user-reported `~/Movies` path), but isn't a documented guarantee - if screenshots end up elsewhere on a different OBS version/platform, `_screenshot_output_dir()` will need to point at the right folder instead.
- The `color_filter`/`opacity` combination for transparency is confirmed on OBS 28+; older OBS versions may not have an opacity property on this filter, in which case the overlay would still appear but fully opaque (blocking the live feed instead of showing through it).
- `obs_frontend_take_source_screenshot()` itself requires a reasonably recent OBS version; if it's missing entirely in your OBS's `obspython` module, `show_freeze_overlay()` will raise an `AttributeError` when called (not caught explicitly - would show up as a Python traceback in OBS's script log).

## Browser-based control panel (`/control`)

An alternative to both this script's Scripts-panel buttons and OBS Hotkeys: `obs_snooker/overlay_assets/control.html`/`.css`/`.js` is a second, separate web page (served by the same `OverlayServer` that serves `/overlay`) with large, touch-friendly buttons for the common scoring actions - per-ball-value potting (red=1 through black=7), `-1` (undo), `wins frame`, `switch turn`, `reset frame score` - plus a small live readout of the current score/turn, for the operator's own feedback.

**How it's meant to be used**: add `http://127.0.0.1:<port>/control` as its own OBS **Browser Source** (separate from the `/overlay` one used for the broadcast graphic) - it doesn't need to be visible on stream, so keep it on an unused scene or just hidden. Then right-click that source in OBS and choose **"Interact"** - this opens a live, fully-interactive window into that embedded page (a standard OBS Browser Source feature, not something this project implements), where the buttons can be clicked directly, without ever opening this script's Scripts-panel dialog or needing a keyboard/hotkey at all. Useful e.g. for a touchscreen tablet next to the table operated by a scorer/referee.

**How it's wired** (`obs_snooker/overlay_server.py`):
- A new `POST /api/action` endpoint on the same HTTP server, taking a small JSON body like `{"action": "pot_ball", "player": 1, "ball": "black"}` or `{"action": "add_points", "player": 2, "value": -1}`, and dispatching it directly onto the shared `MatchState` instance (`add_frame_points`/`win_frame`/`switch_turn`/`reset_frame_scores`/`set_frame_score`/`set_frames` - the same methods `obs-snooker.py`'s own button/hotkey callbacks use). Responds with the same JSON shape as `GET /api/score`, so the control page's JS can immediately refresh its own live readout from the response without a second round-trip.
- Deliberately has **no** "reset match" action, for the same reason it has no hotkey either (see the OBS Hotkeys section above): a destructive, rarely-needed action shouldn't be reachable from a single easily-mis-clicked touch button.
- Malformed/unknown requests (bad JSON, unknown `action`, missing/invalid `player`, unknown `ball` name) get a `400` JSON error response (`{"error": "..."}`), which `control.js` surfaces in a small status line so a mis-click or a stale client is visible immediately rather than silently doing nothing.
- `control.js` polls `GET /api/score` on the same 500ms-ish cadence as `overlay.js`/the scoreboard window, so the control page's own live readout stays correct even if the state was changed by some *other* input path (a hotkey, the Scripts panel, or another browser tab) since the last click.

**Thread-safety note**: `/api/action` requests run on the `OverlayServer`'s own background HTTP thread(s) - a *different* thread than the one OBS uses for this script's own hotkey/button callbacks. Both ultimately mutate the same `MatchState` instance. A `threading.Lock` (`OverlayServer._action_lock`) serializes concurrent `/api/action` requests against *each other* (e.g. two rapid clicks), but there is **no** cross-thread lock shared with `obs-snooker.py`'s own callback path - two different actions arriving from both input paths at almost the exact same instant could still interleave in an unexpected order, though Python's GIL keeps individual attribute reads/writes from actually corrupting data. This is treated as an acceptable risk for a hobby scoreboard tool (same category as a referee and an operator both trying to score the same shot in the same instant) rather than adding a full cross-thread locking scheme across two different modules.

**LAN access (connecting from a phone/tablet)**: `obs-snooker.py` binds the overlay/control HTTP server to `OVERLAY_BIND_HOST = "0.0.0.0"` (all network interfaces), not just `127.0.0.1`, so the `/overlay` and especially `/control` pages can be opened directly from another device's browser on the same local network (e.g. a phone sitting next to the table) - not just from inside an OBS Browser Source on the same machine. `"0.0.0.0"` is the standard cross-platform wildcard bind address (works the same on macOS, Windows, and Linux). On `script_load()`/whenever the overlay port changes, `_log_overlay_urls()` prints both a `127.0.0.1` URL (for this machine) and, via `_local_lan_ip()`, a LAN-IP URL to try from another device - that helper uses the standard "connect a UDP socket to an external address, then read back which local IP the OS would have used" trick (no packets are actually sent; UDP `connect()` only sets up routing), which needs no extra dependencies and works identically cross-platform, unlike parsing `ifconfig`/`ipconfig` output.
- **Important cross-platform subtlety**: `OverlayServer.url`/`control_url`/`score_url` always report `127.0.0.1` (via the `_connectable_host` property), never the raw `0.0.0.0` bind address, even though the server actually listens on all interfaces. This matters because connecting a *client* socket to `0.0.0.0` is unreliable across platforms (notably unreliable on Windows) - a server bound to `0.0.0.0` always still accepts connections to `127.0.0.1` too, so that's what same-machine consumers (the scoreboard window subprocess's `--url` argument, and the "open this in a browser" log message) should use.
- **Security note**: binding to all interfaces means anyone on the same local network can reach `/control`'s scoring actions without any authentication. Acceptable for a typical home/club LAN, but be mindful if this machine is ever connected to a shared/untrusted network.

## Notes for agents

- **OBS's "Reload Scripts" does not reload submodules - real bug hit during development**: OBS's "Reload Scripts" button only re-executes the top-level `obs-snooker.py` file from scratch; it does **not** clear Python's own `sys.modules` cache. So any `obs_snooker.*` submodule that was already imported in a previous load keeps running its *old* in-memory code even after editing the file on disk and clicking "Reload Scripts" - this caused a real, confusing `AttributeError` during development (`obs-snooker.py`'s fresh code called a new `OverlayServer.control_url` property that only existed in the on-disk source, while the cached `obs_snooker.overlay_server` module object already in `sys.modules` predated that change). **Fix**: `obs-snooker.py` now explicitly deletes every `obs_snooker`/`obs_snooker.*` entry from `sys.modules` *before* importing any of them, forcing a genuinely fresh import on every run - so "Reload Scripts" alone is now sufficient after editing any file under `obs_snooker/`, without needing a full OBS restart. If you add new submodules to the `obs_snooker` package, no extra action is needed - the prefix-based `sys.modules` cleanup picks them up automatically.
- The project targets OBS Studio and its Python scripting API (`obspython`), which is only available inside a running OBS instance – it cannot be installed via pip. Only `obs-snooker.py` imports it; keep it that way so the rest of the code stays testable outside OBS.
- `requirements.txt` contains only dependencies installable outside of OBS (e.g. `pynput`). Tkinter is part of the Python standard library and is not listed there, but it must be available in the Python installation configured in OBS's Python settings (on some Linux distros this requires a separate system package, e.g. `python3-tk`). The browser overlay uses only the standard library (`http.server`, `json`, `threading`, `pathlib`) – no extra dependency needed for it.
- `requirements-dev.txt` lists development-only dependencies (currently just `pytest`) needed to run `tests/` outside of OBS.
- Code and comments in this repository should be written in English.
- **Cross-platform GUI requirement (macOS + Windows):** both the scoreboard window and the browser overlay must work with OBS on both operating systems.
  - Scoreboard window: **Tkinter** (stdlib, available on both macOS and Windows Python installations, no extra native dependencies), but launched as a **separate OS process** (see "Scoreboard window process" above) rather than created inside OBS's own interpreter. This sidesteps a real macOS crash (Tk-in-foreign-Cocoa-host) and is unlikely to hurt on Windows either, since Windows has no equivalent single-`NSApplication`-per-process constraint - a plain `Tk.mainloop()` in its own process is the simplest, most standard way to run a Tkinter GUI there too.
  - Browser overlay: a plain `http.server.ThreadingHTTPServer` has no main-thread requirement, so `OverlayServer` runs it in a background daemon thread on both macOS and Windows without issue. The overlay page itself (`overlay.html`/`.css`/`.js`) polls `/api/score` every 400ms via `fetch`; keep `html, body { background: transparent; }` in `overlay.css` so OBS's Browser Source shows only the scoreboard graphic, not a solid box, over the camera feed. `overlay.css` also `@import`s the "Oswald" font from Google Fonts for the condensed bold broadcast look, with a system-font fallback (`Arial Narrow`/sans-serif) if OBS's embedded browser has no internet access.
  - Communication between the keyboard listener / OBS properties and the browser overlay is done via a single shared in-process `MatchState` instance (`OverlayServer` reads it live on each request). The scoreboard window process, being a separate process, instead polls the same overlay server's `/api/score` JSON endpoint - see "Scoreboard window process" above.
- **OBS button callback limitation:** `obs_properties_add_button` callbacks only receive `(props, prop)`, not the current `settings` object. To let the "+points" buttons and the Python-interpreter override read auxiliary property values, `obs-snooker.py` caches the most recent `settings` object at module level (`current_settings`, updated in `script_update`) and reads from it inside the button callbacks.
- **Reduced/mismatched OBS Python environments:** OBS's "Python Install Path" setting must point at a Python installation that actually exists on disk and matches the interpreter OBS embeds - e.g. with Homebrew's `python@3.11` formula, `brew upgrade` deletes the old versioned Cellar directory (e.g. `.../python@3.11/3.11.12_1/...`), silently breaking that setting until it's updated to the new version path. When OBS's configured path is stale/wrong, its embedded interpreter can end up with a broken `sys.path` where even basic pure-Python stdlib modules (`dataclasses`, `http.server`, etc.) fail with `ModuleNotFoundError`, while compiled/frozen modules (`os`, `sys`, `threading`) still work - this looks like a code bug but is an environment/configuration issue. Prefer Homebrew's stable `opt` symlink (e.g. `/opt/homebrew/opt/python@3.11/Frameworks`) over a version-pinned `Cellar` path in OBS's Python settings, since the former survives future `brew upgrade`s. For this same reason, avoid adding new pure-Python-only stdlib dependencies without checking whether they might be similarly affected in a given user's OBS setup.
- **`pynput`'s macOS keyboard backend crashes OBS via a background-thread TSM call - real root cause and fix:** `keyboard.Listener` is itself a `threading.Thread` subclass, so `.start()` always spawns its own background thread to run `_run()` - **regardless of which thread calls `.start()`**. On macOS, `Listener._run()` (in `pynput/keyboard/_darwin.py`) unconditionally calls `pynput._util.darwin.keycode_context()` on that background thread to read the current keyboard layout via several Carbon/Text-Services-Manager (TSM) functions (`TISCopyCurrentKeyboardInputSource`, `TISGetInputSourceProperty`, ...). Inside a real Cocoa host application with its own main dispatch queue - such as OBS - making these TSM calls off the main thread aborts the whole process with `SIGTRAP`/`dispatch_assert_queue_fail` inside `TSMGetInputSourceProperty`. (An earlier attempted fix - calling `start_keyboard_listener()` directly instead of wrapping it in an extra `threading.Thread` - did **not** resolve this, since the crash happens on the listener's own internal thread either way; reproducing a bare `pynput.keyboard.Listener` in a plain Terminal Python process also does not crash, since a plain script has no main dispatch queue to violate - this is specifically an interaction with a real Cocoa/Qt host app's main queue, which only shows up inside OBS itself.) **Fix:** `obs_snooker/darwin_keycode_patch.py`'s `apply_macos_keycode_context_workaround()` - called from `start_keyboard_listener()` before constructing the `Listener` - pre-computes the keyboard-layout context once on the *caller's* thread (safe, since `start_keyboard_listener()` is called from `script_load()` on OBS's main thread) and monkeypatches `pynput.keyboard._darwin.keycode_context` to hand back this cached value instead of touching Carbon/TSM again from the listener's background thread. It is a no-op on non-macOS platforms and fails safe (logs a message, leaves pynput's default behavior in place) if a future pynput release changes these internals. See `tests/test_darwin_keycode_patch.py` (macOS-only) for coverage. The macOS Accessibility permission (System Settings → Privacy & Security → Accessibility) must also be granted to OBS for the listener to actually receive key events, independent of this crash.
